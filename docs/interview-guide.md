# AgentForge 面试指南（120 题）

使用方法：先练每题的“30 秒”，再练前 40 题的“2 分钟深挖”。回答时始终给出代码证据和边界，不把设计目标说成已经验证的生产结论。

## A. 核心设计题（1–40，含深挖）

### 1. 为什么自研 Agent Loop，而不直接使用 LangChain4j？

- 要点：控制流可解释；恢复与预算是一等语义；依赖更小。
- 30 秒：这个项目的目标是展示后端 Agent 原理，所以我把模型、工具、策略和存储定义成 SPI，自研一个确定性 Loop。这样每次状态迁移、预算检查、intent/result 写入都能定位；代价是少了框架生态，生产中会按团队集成成本重新评估。
- 2 分钟深挖：框架擅长快速接 Provider 和工具，但隐藏的重试、消息转换和 memory 行为会影响审计。AgentForge 只让模型负责规划，执行由 Java 决定；Provider 仅在边界适配。恢复时需要知道工具是否完成，这要求 Loop 和事件流共同设计，后贴一个 memory store 不够。
- 项目证据：`AgentEngine`、`DefaultAgentEngine`、scripted model 测试。
- 权衡与追问：扩展速度换可控性；追问“何时迁回框架？”——当框架能保持事件语义并显著降低 Provider 维护成本。

### 2. Agent 与普通 ChatBot 的本质差异是什么？

- 要点：闭环；工具副作用；状态和终止。
- 30 秒：ChatBot 主要生成答案，Agent 会观察环境、规划 ToolCall、执行并把结果回灌，形成闭环。闭环引入权限、重复调用、费用和崩溃恢复，所以关键不只是 prompt，而是受控执行状态机。
- 2 分钟深挖：Agent 的输出会改变工作区，因此要把“生成”和“执行”隔离。模型输出不是命令，而是候选调用；注册表、Schema、Policy、Sandbox 逐层收窄能力。每轮有明确 usage 和 termination reason。
- 项目证据：ToolCall → PolicyDecision → ToolResult 链路。
- 权衡与追问：自治程度越高风险越大；追问可用“按风险逐步自动化”。

### 3. 为什么选择 Java 21？

- 要点：后端生态；record；虚拟线程；长期可维护。
- 30 秒：Java 21 的 record 很适合不可变工具参数和事件，sealed/enum 适合状态建模，虚拟线程适合大量阻塞 I/O；同时 Spring、Jackson、SQLite 和 Maven 生态贴近后端岗位。
- 2 分钟深挖：虚拟线程不等于无限并发，仍需并发上限、超时和取消。record 降低反射绑定的不确定性，但需要限制泛型和多态类型。Java 的显式接口也让 Provider、Policy、Store 可单测替换。
- 项目证据：`ToolHandler<A extends Record>`、`RunStatus`、执行器。
- 权衡与追问：启动/内存不如 Go；换来成熟 DI 和类型生态。

### 4. 四模块为什么这样拆？

- 要点：依赖方向；领域与基础设施隔离；可替换测试。
- 30 秒：core 只含状态机和 SPI；infrastructure 实现模型、工具、沙箱、SQLite；cli 负责装配与交互；eval 负责实验。core 不依赖 Spring/SQLite，所以 scripted model 和内存 store 能快速测试。
- 2 分钟深挖：模块边界不是按技术名词随意拆，而是约束依赖方向。CLI 可以换成服务端，Store 可以换 PostgreSQL，状态机无需改。eval 独立避免评测逻辑污染生产 Loop。
- 项目证据：父 POM modules 与各 module POM。
- 权衡与追问：模块化单体比微服务简单；当前没有跨进程需求。

### 5. 一次 run 的数据流是什么？

- 要点：初始化、压缩、模型、校验、策略、执行、回灌。
- 30 秒：创建 session 并落事件，准备上下文，调用流式模型；没有工具就完成，有工具则按名称查注册表，做参数和策略校验，必要时审批，执行前写 intent，执行后写 result，把结果作为 tool message 回到下一轮。
- 2 分钟深挖：预算在调用前和 usage 返回后各检查一次；模型响应和工具结果都有 checkpoint。未知工具和拒绝也作为结构化结果返回，避免异常直接终止可修复任务。
- 项目证据：`DefaultAgentEngine.executeLoop`。
- 权衡与追问：串行写工具牺牲吞吐，换取工作区一致性。

### 6. 状态机如何避免非法状态？

- 要点：显式 enum；事件驱动；终态不可继续。
- 30 秒：用 `RunStatus` 区分运行、等待审批、成功、失败、取消、预算耗尽和不确定，返回值同时带 `TerminationReason`。恢复先验证事件链和快照，不从终态随意重跑。
- 2 分钟深挖：状态表示“现在处境”，reason 表示“为什么结束”，二者分离后统计才准确。`UNCERTAIN` 不是 FAILED，因为需要人工确认副作用。
- 项目证据：`RunStatus`、`TerminationReason`、resume 测试。
- 权衡与追问：目前没有形式化 transition table；可演进成显式 reducer。

### 7. 为什么预算要多维？

- 要点：次数、时间、token、费用、重复调用覆盖不同失控方式。
- 30 秒：只有最大轮数挡不住单轮超长响应，只有 token 挡不住慢工具，所以我同时限制迭代、墙钟、输入/输出 token、费用和重复调用，并记录具体终止原因。
- 2 分钟深挖：费用依赖 Provider usage 和价格快照；墙钟用 Clock 便于测试；重复调用使用去掉 call id 的指纹。检查点放在模型调用前后，防止预算已超仍执行副作用。
- 项目证据：`RunBudget`、`budgetReason`。
- 权衡与追问：硬上限可能中断可完成任务；可按任务风险给配置模板。

### 8. 如何检测 Agent 死循环？

- 要点：调用指纹；连续阈值；全局预算兜底。
- 30 秒：对工具名和参数生成稳定指纹，忽略每轮变化的 call id；连续三次相同就终止为 `REPEATED_TOOL_CALL`。即使参数微变绕过，迭代和时间预算仍兜底。
- 2 分钟深挖：连续重复比全局去重合理，因为读工具在不同阶段可能合法重复。更高级方案可加入观察结果哈希和语义相似度，但会增加误判。
- 项目证据：重复调用单测。
- 权衡与追问：三次是经验默认值，不是普适常数。

### 9. 为什么上下文在 75% 时压缩？

- 要点：留输出/工具余量；降低突发溢出；阈值可配置。
- 30 秒：不能等 100% 才处理，因为下一轮输出、工具 Schema 和协议开销还占窗口。75% 给增长留余量，同时避免过早丢信息。
- 2 分钟深挖：保留系统指令、第一用户目标和最近消息，把中段变成确定性摘要；记录压缩前后估算。阈值需要按模型窗口、最大输出和工具数量校准。
- 项目证据：`ContextManager` 与压缩测试。
- 权衡与追问：确定性摘要可复现但语义弱；模型摘要相反。

### 10. 上下文压缩怎样避免丢失关键约束？

- 要点：固定保留；结构化事实；可审计。
- 30 秒：系统提示和首个用户任务永不进入被裁剪区，最近交互完整保留，中间历史形成带标记摘要；每次压缩写事件，便于排查错误是否由丢上下文造成。
- 2 分钟深挖：理想摘要应分为目标、已修改文件、测试结果、未决风险和审批决定，不能只做自然语言拼接。当前版本选择确定性裁剪，并把语义摘要列为演进项。
- 项目证据：`ContextPreparation`。
- 权衡与追问：保留更多提高质量但增加费用。

### 11. 为什么 Provider 要分别做契约测试？

- 要点：相似不等于相同；字段、结束、usage 和 tool result 都不同。
- 30 秒：DeepSeek 是 SSE/OpenAI-compatible，Ollama 是 NDJSON；结束标志、usage、tool result 字段都不同。共用领域消息，但不共用解析状态机，分别测试任意碎片和异常。
- 2 分钟深挖：所谓 compatible 往往只覆盖请求大框架，流式 delta 细节最容易不同。把协议差异压在 adapter 中，core 只看完整 `ModelResponse`。
- 项目证据：两个 parser test 与 `ModelRequestJsonTest`。
- 权衡与追问：重复少量解析代码换更清楚的失败边界。

### 12. ToolCall 为什么必须聚合完整后再校验？

- 要点：流碎片不是合法 JSON；多调用交错；避免半参数执行。
- 30 秒：流中 name 和 arguments 可能拆在任意位置，多工具按 index 交错。只有 `[DONE]` 或结束事件后，才能把 accumulator 变成完整调用，再做 JSON、Schema 和权限校验。
- 2 分钟深挖：若边收边执行，`{"path":"src/` 这种半参数可能被错误解释；也无法确认后续是否改变工具名。sink 可以展示增量，但执行通道只接受完成对象。
- 项目证据：fragment parser tests。
- 权衡与追问：等待完整调用增加一点延迟，但执行安全优先。

### 13. 介绍一下你独立开发的 CLI 编程 Agent，核心模块有哪些？

- 要点：core、infrastructure、cli、eval；模型是不可信规划器。
- 30 秒：AgentForge 是 Java 21 的 CLI 编程 Agent。core 管状态机、上下文和预算；infrastructure 管 DeepSeek/Ollama、工具、策略、Docker 与 SQLite；cli 用 Spring Boot non-web 和 Picocli 装配；eval 固定数据和生成报告。
- 2 分钟深挖：它的差异点是执行边界：ToolCall 必须通过注册、Schema、参数、策略和审批；执行前后落审计事件；崩溃后从快照恢复。30 项微基准 30/30，Java20 当前如实记录环境失败。
- 项目证据：四模块 POM、README 架构图。
- 权衡与追问：首版不做 Web、多 Agent、职位搜索，集中证明后端核心。

### 14. 详细描述 Agent Loop 的完整执行流程。

- 要点：上下文压缩→流式模型→工具检测→注册校验→参数校验→权限→执行→大结果处理→审计→返回。
- 30 秒：Loop 先检查预算并在 75% 窗口压缩，再流式调用模型、按 index 聚合 ToolCall；随后做工具注册、Schema/参数、策略和审批，写 intent 后在沙箱执行，截断大输出，写 result 和快照，再把 ToolResult 回灌。
- 2 分钟深挖：无 ToolCall 视为最终答案；调用前后都检查预算；未知工具/非法参数/拒绝作为结构化错误进入下一轮；连续三次相同调用熔断。任何非幂等 intent 没有 result，恢复为 UNCERTAIN。
- 项目证据：`DefaultAgentEngine`、`ContextManager`、事件类型。
- 权衡与追问：大结果目前截断，后续可内容寻址存储并只回灌摘要。

### 15. Agent Loop 的循环终止条件有哪些？

- 要点：无工具最终回答、超时、迭代、输入/输出 token、费用、重复、用户终止、不可恢复错误。
- 30 秒：正常终止是模型返回无 ToolCall 的最终答案；保护性终止包括 30 轮、20 分钟、200k 输入、30k 输出、费用上限和三次重复；还预留用户取消与不可恢复错误。
- 2 分钟深挖：每个条件对应单独 reason，方便报告分组。预算调用前检查避免无意义请求，usage 返回后再检查避免继续执行副作用；不能把 budget exhausted 统计成模型任务失败。
- 项目证据：`RunBudget` 与终止单测。
- 权衡与追问：阈值按交互式/批量评测分别配置。

### 16. 是否实现 checkpoint、resume、human-in-the-loop？上下文包含哪些信息？

- 要点：已实现；事件+快照；消息、usage、请求、预算、循环状态。
- 30 秒：实现了 SQLite 事件流与最新快照。快照包含完整消息、usage、仓库、任务、Provider、沙箱、预算、迭代数、重复指纹和开始时间；审批请求/决定也是事件。非幂等工具结果未知时恢复为 UNCERTAIN。
- 2 分钟深挖：事件是事实源，快照用于快速恢复；SHA-256 前序哈希检测篡改。CLI 当前审批是同步交互，但状态模型允许扩展为异步队列。恢复先验证链，再检查未配对 intent/result。
- 项目证据：`RunCheckpoint`、`SqliteCheckpointStore`、resume 测试。
- 权衡与追问：SQLite 适合单机 CLI；多实例需事务数据库和租约。

### 17. 如果支持人工介入，你会怎么设计？

- 要点：策略触发；持久化等待态；幂等决定；超时和审计。
- 30 秒：Policy 返回 ASK 时写审批请求和快照，状态转 WAITING_APPROVAL；审批 API 用 session+call id 幂等提交 approve/reject，写决定后继续。超时默认拒绝，所有理由和操作者进入审计。
- 2 分钟深挖：审批页需要展示工具、规范化参数、diff、风险、预计资源而不是原始 prompt。批准范围区分一次、同类会话内和永久规则；永久规则需要单独管理。恢复时不能重复弹已决定请求。
- 项目证据：`ApprovalRequest/Decision/Handler`、CLI 交互。
- 权衡与追问：审批越多越安全但打断体验，可用风险和历史信誉调节。

### 18. ToolCall 的 Java 核心实现逻辑是什么？

- 要点：注解 Bean、泛型 record、Schema、Jackson、执行器；禁止任意动态类。
- 30 秒：Spring 扫描 `@AgentTool` Bean，注册表读取 `ToolHandler<A extends Record>` 的 A，结合 `@ToolParam` 生成 Schema。调用时按工具名取已注册实例，校验 JSON 后绑定 record，再注入 `ExecutionContext` 执行。
- 2 分钟深挖：模型只能指定工具名，不能给类名；因此没有 `Class.forName` 任意实例化风险。Schema 只支持白名单类型，启动时发现不支持签名就失败。执行器被包装为 `ToolDefinition`，策略先看到 risk 和 idempotent。
- 项目证据：`ReflectiveToolRegistry`。
- 权衡与追问：受控类型牺牲复杂对象表达，换确定性和安全。

### 19. 动态传入 JSON 的 Java 方法调用如何实现？

- 要点：安全注册表替代类名定位；方法在启动期确定；JSON 转 record；调用。
- 30 秒：传统做法是类名定位、实例化、方法匹配、参数转换、反射调用，但 AgentForge 不接受模型类名。启动期已把受信 Bean 和唯一 execute 方法注册好，运行时只做工具名查找、Schema 校验、Jackson 转 record 和受控执行。
- 2 分钟深挖：这样避免重载解析、私有方法暴露和构造器副作用。若必须支持重载，应在注册期生成稳定 operation id，而不是运行时凭 JSON 猜方法。转换错误返回结构化 error，最多让模型修正一次。
- 项目证据：工具注册表测试与未知字段测试。
- 权衡与追问：灵活性低于通用 RPC，但攻击面更小。

### 20. JSON Schema 是怎么生成的？

- 要点：record component；注解；受控映射；required/range。
- 30 秒：遍历参数 record components，根据 Java 类型生成 string/integer/number/boolean/array，结合 `@ToolParam` 写 description、required 和数值范围；未知或不支持类型在注册期拒绝。
- 2 分钟深挖：生成与验证必须使用同一元数据，否则 Schema 告诉模型的规则和后端实际规则会漂移。数组还应声明 items；enum 应输出有限集合。生产版可缓存编译后的 validator。
- 项目证据：`ReflectiveToolRegistryTest`。
- 权衡与追问：手写 Schema 更灵活但容易与 record 不同步。

### 21. Schema 校验和 Jackson 绑定谁先？

- 要点：语法/结构先，绑定后；错误稳定。
- 30 秒：先解析 JSON tree，检查 required、unknown、类型和范围，再让 Jackson 转 record。这样不会把宽松强转当合法输入，错误码也比反射异常稳定。
- 2 分钟深挖：绑定后还可做跨字段业务校验；三层分别解决结构、类型构造和业务不变量。错误中不能回显秘密或完整大参数。
- 项目证据：缺字段、错类型、范围测试。
- 权衡与追问：多次遍历有开销，但工具参数很小。

### 22. Schema 自修复怎么做？

- 要点：结构化错误；限制一次；不执行失败调用。
- 30 秒：非法参数不进入工具，返回包含 error code、字段和期望类型的 ToolResult，让模型下一轮修正；专用重试计数最多一次，再失败就终止或要求人处理。
- 2 分钟深挖：修复不是后端猜值，也不能自动放宽 Schema。应以 call lineage 统计，而非全局轮数。当前版本已有结构化错误反馈，独立“一次”计数是明确路线图项。
- 项目证据：README 限制说明。
- 权衡与追问：自动修复提高成功率，也可能增加 token 和延迟。

### 23. Spring DI 在工具系统里起什么作用？

- 要点：生命周期、依赖注入、可替换实现、启动期发现。
- 30 秒：工具是 Spring Bean，可以注入沙箱、配置和客户端；注册表只接收容器认可的 `ToolHandler` 列表，避免运行时任意实例化。测试仍可不用 Spring，直接构造 registry。
- 2 分钟深挖：注解既是组件标记也是工具元数据。重资源对象由容器单例管理，但工具本身应无会话可变状态，ExecutionContext 每次传入。
- 项目证据：`@AgentTool`、配置类。
- 权衡与追问：Spring 增加启动成本，换成熟配置与 DI。

### 24. PolicyEngine 为什么独立于 Tool？

- 要点：关注点分离；统一治理；测试矩阵。
- 30 秒：工具负责“怎么做”，策略负责“是否允许”。独立后同一工具可以按 sandbox、用户、仓库和风险采用不同策略，也能单测完整矩阵。
- 2 分钟深挖：把权限写进工具会分散且易漏；把它只写 prompt 又不可强制。Policy 看规范化调用和执行上下文，输出 ALLOW/ASK/DENY 与理由。
- 项目证据：`DefaultPolicyEngineTest`。
- 权衡与追问：策略配置复杂时可演进成规则引擎，但先保持可读。

### 25. 如何防止路径穿越？

- 要点：拒绝绝对/`..`；normalize；real path；父目录检查。
- 30 秒：先拒绝绝对路径和包含 `..` 的输入，resolve 到 workspace 后 normalize 并校验前缀；已存在路径再取 real path 防符号链接逃逸，新文件校验最近已存在父目录。
- 2 分钟深挖：只做字符串 `startsWith` 会被编码、分隔符和 symlink 绕过；Windows 还要处理盘符、UNC 和大小写。最终打开文件仍应尽量使用已验证的 Path。
- 项目证据：`WorkspaceGuardTest`。
- 权衡与追问：TOCTOU 仍可能存在，强隔离依赖容器挂载。

### 26. 为什么命令必须是 argv，而不是 shell 字符串？

- 要点：不解释元字符；边界清晰；日志可结构化。
- 30 秒：`ProcessBuilder(List<String>)` 直接传 argv，`;`、`&&`、重定向和 `$()` 不会被 shell 展开，大幅减少注入面。命令名还经过 allowlist。
- 2 分钟深挖：如果业务确实需要管道，应建一个显式 pipeline 数据结构逐进程启动，而不是退回 `sh -c`。Windows 与 Linux 参数规则也更可控。
- 项目证据：`LocalSandboxExecutorTest`。
- 权衡与追问：表达能力降低，但对 Agent 是合理最小权限。

### 27. Docker 沙箱提供了哪些边界？

- 要点：断网、非 root、CPU/内存/PID、工作区、超时。
- 30 秒：容器默认 `--network none`、用户 1000、2 CPU、4GB、256 PID，只挂工作区并固定工作目录；宿主还控制超时和输出大小。
- 2 分钟深挖：这些限制分别防数据外传、特权、资源耗尽和目录扩散。Docker 不是 VM，daemon 权限和内核漏洞仍是边界外风险；高风险场景需 gVisor/微虚机。
- 项目证据：`DockerCommandFactoryTest`、Dockerfile。
- 权衡与追问：隔离增强会增加冷启动和依赖镜像成本。

### 28. 本地受限模式安全吗？

- 要点：不是强沙箱；显式开启；只做纵深限制。
- 30 秒：它只有 allowlist、argv、工作目录、超时和输出截断，不能隔离内核、网络或被允许程序的漏洞，所以默认不用，必须显式 `--sandbox local`。
- 2 分钟深挖：本地模式面向开发便利和低风险读操作；文档明确 threat model。不能因为“没有 shell”就称为安全沙箱。
- 项目证据：README 安全边界。
- 权衡与追问：便利与隔离不可兼得，默认应偏安全。

### 29. 工具能并行执行吗？

- 要点：只读且幂等可并行；写与命令串行。
- 30 秒：多个 READ、idempotent 工具可以放虚拟线程并行；文件写、补丁和命令串行，因为它们共享工作区状态，乱序会导致不可复现。
- 2 分钟深挖：并行组需要在同一模型响应内先做依赖分析，结果按原 call index 回灌。取消、超时和并发配额仍不可少。
- 项目证据：工具元数据的 risk/idempotent。
- 权衡与追问：当前版本保守串行，计划对只读批次并发。

### 30. 虚拟线程解决了什么，没解决什么？

- 要点：降低阻塞线程成本；不解决资源、数据竞争、CPU。
- 30 秒：它适合文件、HTTP、子进程等待，让每调用一线程更便宜；但不会让 CPU 任务更快，也不会自动提供超时、背压和线程安全。
- 2 分钟深挖：应使用结构化并发作用域或 executor 管生命周期，设置最大并发，确保请求取消时子任务一起取消。共享工具必须无可变会话状态。
- 项目证据：本地执行器等待实现。
- 权衡与追问：简单阻塞代码换运行时调度，监控方式也要更新。

### 31. 为什么使用事件溯源？

- 要点：恢复、审计、调试、指标重算。
- 30 秒：最终状态解释不了“执行过什么”。append-only 事件保存模型响应、审批、intent、result 和终止原因，既能恢复，也能验证审计链和重新计算指标。
- 2 分钟深挖：事件不可变，快照只是加速；schema 演进需版本化。Agent 的副作用尤其需要 intent/result，因为结果写入前可能崩溃。
- 项目证据：`session_events` 表。
- 权衡与追问：存储更多、查询复杂，换完整事实轨迹。

### 32. SHA-256 哈希链能防什么？

- 要点：检测篡改/删改/重排；不能阻止拥有数据库权限的人重算整链。
- 30 秒：每条事件包含 previous hash，重放校验 sequence、前序和当前哈希，能发现普通篡改、删除或重排。但攻击者若能重写全库可重算，所以强审计还要外部签名或锚定。
- 2 分钟深挖：canonical 字符串字段顺序固定，避免 JSON 顺序导致不一致。可定期把链头签名上传 WORM 存储。
- 项目证据：tamper test。
- 权衡与追问：当前目标是可验证完整性，不宣称不可抵赖。

### 33. 为什么不能承诺工具 exactly-once？

- 要点：数据库与外部副作用无分布式事务；崩溃窗口。
- 30 秒：命令执行和 SQLite 写 result 不是一个原子事务，执行成功后进程可能在落结果前崩溃。除非工具天然幂等或有幂等键，否则只能标 UNCERTAIN，不能自动重放。
- 2 分钟深挖：可通过 outbox、幂等键、事务型资源缩小问题，但 shell/文件系统没有通用两阶段提交。诚实暴露不确定状态比虚假 exactly-once 更正确。
- 项目证据：intent/result 恢复逻辑。
- 权衡与追问：人工介入增加成本，但避免重复破坏。

### 34. SQLite 为什么够用？

- 要点：单机 CLI、事务、WAL、零运维。
- 30 秒：首版是单用户 CLI，SQLite 提供事务、WAL 和成熟 JDBC，又不要求部署服务；事件按 session 顺序追加，写并发低。
- 2 分钟深挖：多实例、远程审批、高并发时需要 PostgreSQL、行锁/租约和对象存储。现在先避免提前分布式化。
- 项目证据：`SqliteCheckpointStore`。
- 权衡与追问：本地文件便携，但备份与权限要由宿主管理。

### 35. 敏感日志如何脱敏？

- 要点：结构化字段递归；Bearer 模式；源头不记录。
- 30 秒：JSON 中 token、key、password、authorization 等字段递归替换，文本中的 Bearer token 也处理；API Key 只从环境读，不进入事件和 manifest。最佳脱敏仍是源头不采集。
- 2 分钟深挖：正则无法覆盖所有秘密，工具输出可能包含源码密钥，因此报告还需大小限制和字段 allowlist。OTLP 不应发送原始 prompt。
- 项目证据：`SensitiveDataRedactorTest`。
- 权衡与追问：过度脱敏降低调试能力，可提供本地受控原始日志。

### 36. 如何设计可观测指标？

- 要点：质量、成本、延迟、安全、恢复。
- 30 秒：按 session/iteration/provider/tool 记录 token、费用、总时长、工具成功率、Schema 错误率、压缩率、审批数和 p50/p95；终止原因和环境失败单独维度。
- 2 分钟深挖：指标分母必须稳定，例如 tool success 不含策略拒绝还是含，要在定义中写清。trace 用于单次因果链，metrics 用于聚合，event 用于审计。
- 项目证据：eval metrics 与事件报告。
- 权衡与追问：高基数字段如 session 不应放长期 metrics label。

### 37. 30 个微基准证明了什么？

- 要点：基础设施不变量；不证明真实修复能力。
- 30 秒：它们快速覆盖流式碎片、Schema、安全、超时、重复、恢复和审计，证明这些确定性组件没有回归；30/30 不能等同 SWE-bench resolved rate。
- 2 分钟深挖：微基准应离线、确定、便宜，适合每次 CI。真实任务依赖模型和镜像，单独报告并保留环境失败。
- 项目证据：`MicroBenchmarkRunner` 和 JSON/CSV。
- 权衡与追问：当前部分 case 是不变量 smoke，后续应更多直接复用生产组件。

### 38. 为什么固定 Java20 数据 revision 和排序？

- 要点：防挑题；可复现；失败不替换。
- 30 秒：固定官方 revision，识别 Java 仓库，对 instance_id 字典序取前 20。这样选择与结果无关，失败题不换，避免只展示漂亮结果。
- 2 分钟深挖：manifest 还要记模型 id、价格、prompt hash、工具版本和预算。数据升级必须新建实验版本，不能覆盖旧报告。
- 项目证据：`Java20ManifestTest`。
- 权衡与追问：前 20 不一定代表全部 Java，但规则透明。

### 39. baseline 和 full 怎样公平比较？

- 要点：同题、同模型、同预算、一次只改目标变量。
- 30 秒：固定前 10 题，同一模型版本、prompt、工具、步骤、时间和价格；baseline 用朴素窗口/原始错误，full 开压缩、结构化 Schema 错误和索引。环境失败不计 resolved 分母。
- 2 分钟深挖：一次运行噪声大，所以只能说观察结果，不能轻易说统计显著。应公开逐题配对差异和成本，而不是只报平均提升。
- 项目证据：evaluation 文档。
- 权衡与追问：控制变量降低外部有效性，但便于归因。

### 40. 当前项目最大的不足是什么？

- 要点：Java20 未完整运行；确定性摘要弱；异步审批/OTLP 未完成。
- 30 秒：当前最重要的限制是完整 SWE-bench harness 尚未执行，所以 Java20 只有环境失败记录，不能声称真实 resolved；另外摘要偏机械，异步审批和 OTLP 仍是路线图。
- 2 分钟深挖：我选择明确暴露限制而不是补假数据。下一步先跑通官方 harness 并保留失败，再用配对 10 题验证 full 是否真的优于 baseline；若无提升，分析 token、Schema 和工具轨迹。
- 项目证据：README 限制和原始报告。
- 权衡与追问：项目完整度与证据可信度之间，优先可信度。

## B. Java、协议、安全与工程题（41–120）

### 41. record 为什么适合工具参数？
- 要点：不可变、组件可反射、值语义。
- 30 秒：record 明确列出参数，Jackson 和 Schema 都能从同一组件元数据生成；不可变也避免执行期间被修改。

### 42. 泛型擦除后怎样得到 `ToolHandler<A>` 的 A？
- 要点：启动期读取实现类 generic interface；拒绝无法解析类型。
- 30 秒：注册时检查实现类的参数化接口并提取 record Class；若代理或多层泛型无法可靠解析，就启动失败而不是猜测。

### 43. Spring 代理会影响泛型反射吗？
- 要点：代理类可能丢签名；取 target class。
- 30 秒：需要用 Spring 的目标类解析工具取得原始实现类，再读泛型；当前简单 Bean 足够，加入 AOP 时要补代理契约测试。

### 44. Jackson 为什么要拒绝未知字段？
- 要点：防拼写静默；避免模型误以为参数生效。
- 30 秒：未知字段如果被忽略会产生“看似成功但行为不同”的调用，所以 Schema 层明确拒绝并回字段级错误。

### 45. JSON number 到 Java int 有什么风险？
- 要点：溢出、小数截断、科学计数。
- 30 秒：先检查节点类型和范围，再绑定；不能依赖 Jackson 宽松转换把 1.2 或超大 long 变成 int。

### 46. 工具错误为什么不直接抛出终止 Loop？
- 要点：可修复错误回灌；系统错误才终止。
- 30 秒：未知工具、非法参数和策略拒绝是模型可修正的观察，应该作为 ToolResult；数据库损坏等不可恢复错误才结束会话。

### 47. SSE parser 如何处理 keep-alive？
- 要点：忽略空行和冒号注释；只消费 data。
- 30 秒：SSE 的空行和 `: keep-alive` 不是 JSON，解析器先按字段识别，只把 `data:` 交给 JSON 层。

### 48. NDJSON 断在半行怎么办？
- 要点：按流缓冲到换行；结束仍不完整则协议错。
- 30 秒：网络 chunk 不是记录边界，必须累积字符直到换行；EOF 时残留无法解析就报断流而非静默丢弃。

### 49. 多 ToolCall 如何保持顺序？
- 要点：index 聚合；结果按原 index 排序。
- 30 秒：每个 index 一个 accumulator，完成后按 index 构造列表；即使 delta 交错，回灌顺序仍稳定。

### 50. usage 缺失如何计费？
- 要点：标记 estimated；本地估算；不能当零。
- 30 秒：优先 Provider usage；缺失时本地 tokenizer/估算并标 estimated，预算采取保守值，报告不能把缺失当免费。

### 51. DeepSeek 价格为什么写进 manifest？
- 要点：价格会变；结果可复算。
- 30 秒：相同 token 在不同日期成本不同，manifest 固定单价和抓取时间，才能解释费用并用新价格重算。

### 52. 为什么费用上限检查用实际 usage？
- 要点：账单更准；请求前仍需预测。
- 30 秒：响应后用 Provider usage 累加最准确；请求前用已消费和最大输出做保守预判，避免最后一轮大幅越界。

### 53. HTTP 429 如何处理？
- 要点：读取 Retry-After；有界指数退避；计入墙钟。
- 30 秒：只对可重试传输错误做带抖动的有限退避，重试仍消耗总时间预算；不能重试已可能执行的工具。

### 54. 模型流中断后能否续传？
- 要点：通常不能精确；整次重试要幂等且有预算。
- 30 秒：Chat streaming 没有通用 offset，半响应不执行工具；可重发完整请求，但要记录 attempt 并限制次数。

### 55. Prompt injection 如何防？
- 要点：仓库内容是不可信数据；能力控制不靠 prompt。
- 30 秒：系统提示提醒不可信只是软防线，真正边界是注册白名单、Schema、Policy、审批和 Sandbox；README 中的恶意文字不能新增权限。

### 56. 工具描述会不会被仓库内容污染？
- 要点：描述来自代码常量；仓库只进 data message。
- 30 秒：工具 Schema/描述由受信代码生成，不从仓库拼接；检索内容必须清晰标记为不可信观察。

### 57. 符号链接检查为何仍有 TOCTOU？
- 要点：检查和打开之间可替换。
- 30 秒：real path 检查后目标仍可能被并发换成链接；容器挂载限制是第二层，严格方案用安全目录句柄或禁止并发外部修改。

### 58. 如何限制大文件读取？
- 要点：大小阈值、范围读取、二进制检测。
- 30 秒：stat 后限制字节数，默认按行/范围读取，检测 NUL/编码；结果再做输出截断，避免上下文和内存被撑爆。

### 59. Patch 工具为什么不用让模型写整文件？
- 要点：diff 小、冲突可检测、审计清楚。
- 30 秒：精确旧块替换能确认模型基于当前内容，减少覆盖用户改动；整文件写入更容易丢并发修改。

### 60. 如何保证 Patch 原子性？
- 要点：临时文件、fsync、原子 move；先校验唯一旧块。
- 30 秒：完整生成新内容并校验后写同目录临时文件，再原子替换；当前实现是最小版本，生产需补 fsync 和平台降级。

### 61. Git status/diff 为什么是只读工具？
- 要点：提供观察；不改变仓库。
- 30 秒：它们让模型验证改动但不执行 commit/push；远程 Git 默认不开放，符合最小权限。

### 62. 为什么不提供 shell 工具？
- 要点：能力过宽；难以做细粒度策略。
- 30 秒：通用 shell 等于把解析和权限交给模型，argv + allowlist 可以逐个命令审计并阻断元字符解释。

### 63. allowlist 是否足够？
- 要点：不够；被允许程序也有复杂能力。
- 30 秒：例如 git 或 java 也可能读写/联网，所以还要容器网络、挂载、用户、资源和策略；allowlist 只是其中一层。

### 64. 输出截断要保留头还是尾？
- 要点：两端；标记省略字节。
- 30 秒：错误原因常在尾部、上下文在头部，最好保留 head+tail 并明确 truncated 与原始大小。

### 65. 超时后如何清理子进程？
- 要点：进程树/容器；先温和后强制。
- 30 秒：本地模式需要销毁整个 descendants，Docker 则停止容器；仅杀父进程可能泄漏子进程。

### 66. Windows 与 Linux 沙箱有何差异？
- 要点：路径、进程树、权限、Docker mount。
- 30 秒：Windows 有盘符/UNC、大小写和不同进程终止语义；核心用 Path API，CI 双平台跑 Java 测试，强沙箱集成放 Linux。

### 67. 为什么 CI 要 Linux + Windows？
- 要点：Java 跨平台不等于路径/脚本跨平台。
- 30 秒：Windows 捕获路径和换行问题，Linux 验证 Docker 安全参数；两者都跑 `mvnw verify`。

### 68. Maven Wrapper 的价值？
- 要点：固定 Maven 分发；降低环境差异。
- 30 秒：仓库自带 wrapper，CI 和面试官不用预装相同 Maven；依赖版本仍由 POM 锁定。

### 69. 为什么选择 Picocli？
- 要点：强类型参数、子命令、测试方便、Spring 集成。
- 30 秒：它能把 CLI 契约直接映射字段并生成帮助，命令可用内存 out/err 测试，适合 non-web Spring Boot。

### 70. doctor 应检查什么？
- 要点：Java、Docker daemon、镜像、Ollama、Key、workspace。
- 30 秒：区分“命令存在”和“服务可用”，输出可操作失败原因；Ollama 是可选 WARN，默认 Docker 不可用是 FAIL。

### 71. CLI 退出码如何设计？
- 要点：0 成功；参数/环境/任务失败分开。
- 30 秒：脚本需要稳定退出码，不能所有失败都返回 1；报告中还保留细粒度 reason。

### 72. session list/show 有什么用途？
- 要点：可运维；定位审批、恢复和审计。
- 30 秒：list 找 session，show 查看验证后的事件序列；它把“黑盒 Agent”变成可追溯任务。

### 73. report 为什么支持 Markdown 和 JSON？
- 要点：人读与机器集成。
- 30 秒：Markdown 便于复盘和面试展示，JSON 便于流水线聚合；两者共用验证过的事件和脱敏逻辑。

### 74. SQLite WAL 的作用？
- 要点：读写并发；崩溃恢复。
- 30 秒：WAL 允许读者不阻塞单写者，适合 CLI 同时查看会话；仍要控制 checkpoint 和文件权限。

### 75. 事件 sequence 如何生成？
- 要点：session 内单调；Store 验证期望值。
- 30 秒：Engine 维护 next sequence，Store 查询最后事件并拒绝跳号/重复，避免并发或恢复写坏链。

### 76. 快照多久保存？
- 要点：关键边界优先；可叠加每 N 事件。
- 30 秒：模型响应和工具结果后保存可恢复状态；大量事件时可每 25 条快照，关键副作用边界仍立即保存。

### 77. 快照损坏怎么办？
- 要点：回退事件重放；校验；不可恢复则失败。
- 30 秒：快照不是事实源，先验证事件链；有 reducer 时可重建。当前缺少完整 reducer 时应明确 UNRECOVERABLE，而不是猜状态。

### 78. schema migration 怎么做？
- 要点：向前迁移、版本字段、兼容读取。
- 30 秒：数据库启动时只做幂等新增，事件 payload 应加版本；破坏性迁移需要备份和独立命令。

### 79. 审计链为什么用 canonical 字符串？
- 要点：序列化稳定。
- 30 秒：JSON 属性顺序可能变化，固定字段顺序和换行组合能保证不同运行时计算同一哈希。

### 80. 如何防日志注入？
- 要点：结构化编码；换行转义；不要拼接终端控制符。
- 30 秒：JSON logger 让库负责转义，Markdown 表格转义竖线；输出终端时应过滤 ANSI 控制符。

### 81. p50/p95 为什么比平均值重要？
- 要点：尾延迟；Agent 串行放大慢调用。
- 30 秒：平均值会掩盖少量极慢工具，而 Agent Loop 总时长常被尾部调用支配，p95 更能发现超时风险。

### 82. resolved rate 分母怎么定？
- 要点：固定总题与可执行题都报告；环境失败单列。
- 30 秒：同时报告 resolved/固定 20 和 resolved/实际可执行，不能悄悄移除环境失败，更不能替换失败题。

### 83. 测试通过率和 resolved rate 有何区别？
- 要点：部分测试 vs 官方全部判定。
- 30 秒：测试通过率可反映局部进展，resolved 要满足官方 FAIL_TO_PASS/PASS_TO_PASS 条件；两者不能混叫成功率。

### 84. 工具成功率高是否代表 Agent 强？
- 要点：不代表；可能一直成功读错文件。
- 30 秒：它只表示执行可靠，任务质量还看选择工具、补丁和最终测试；需与 resolved、步数、成本联合看。

### 85. Schema 错误率能说明什么？
- 要点：模型-工具接口契合度。
- 30 秒：高错误率可能是模型弱，也可能是描述/Schema 不清；配合修复成功率和 token 才能定位。

### 86. 压缩率越高越好吗？
- 要点：不是；可能损害任务信息。
- 30 秒：压缩率是成本指标，不是质量指标，必须和 resolved、重试与遗漏错误一起看。

### 87. 单次评测能说“提升”吗？
- 要点：只能描述观察；随机性。
- 30 秒：固定配置各一次适合工程烟测，不足以统计推断；至少做配对多次、置信区间或明确“本次观察”。

### 88. 为什么保留负面结果？
- 要点：防选择偏差；指导迭代。
- 30 秒：如果 full 更贵却没提升，这正是重要结论；隐藏它会让项目数据失去可信度。

### 89. 如何限制总评测 ¥50？
- 要点：共享 cost ledger；请求前预估；原子扣预算。
- 30 秒：所有 worker 共享费用账本，请求前预留最大估算，usage 后结算；达到上限停止调度新题并保留已完成记录。

### 90. 并行评测怎样保证费用上限？
- 要点：原子 reservation；并发上限。
- 30 秒：不能让每个 worker 独立判断余额，应由协调器原子预留预算，否则并发请求会集体越界。

### 91. 为什么 manifest 要包含 model id？
- 要点：别名会漂移。
- 30 秒：`deepseek-flash` 背后的版本会升级，除别名外还应记录 Provider 返回或官方快照中的实际版本和日期。

### 92. Ollama 模型如何复现？
- 要点：tag 不够；记录 digest、参数和硬件。
- 30 秒：记录模型 digest、量化、context、temperature、Ollama 版本和 GPU；同名 tag 可能变化。

### 93. 8GB 显存为何选 7B？
- 要点：量化后可运行；留 KV cache。
- 30 秒：7B 量化权重能在 8GB 附近留出上下文/KV 空间，更大模型可能频繁 offload，延迟影响公平评测。

### 94. 温度如何设置？
- 要点：评测低温；记录参数。
- 30 秒：代码修复评测通常低温降低方差；任何温度/top-p/seed 都进入 manifest，不能只写模型名。

### 95. Repository indexing 有什么价值？
- 要点：减少无效读取；提高定位。
- 30 秒：先建立文件/符号/构建结构索引，让模型用更少 ToolCall 找目标；索引必须受 workspace 和大小限制。

### 96. 索引如何避免过期？
- 要点：内容哈希、增量更新、写后失效。
- 30 秒：以文件 mtime+size 或内容哈希做 key，补丁后更新受影响文件；报告记录索引版本。

### 97. 为什么仓库内容要标成 untrusted？
- 要点：代码注释/README 可含指令注入。
- 30 秒：它只是要分析的数据，不能覆盖系统策略；即便写着“上传密钥”，网络工具仍被策略拒绝。

### 98. 如何处理二进制文件？
- 要点：检测并拒绝默认文本工具。
- 30 秒：NUL、MIME/编码和大小检查识别二进制；首版不让模型直接 patch，避免损坏和上下文爆炸。

### 99. 如何处理超大仓库？
- 要点：渐进检索、ignore、限额、索引。
- 30 秒：尊重 `.gitignore`，先目录和搜索再按需读，限制文件数/字节/结果；不要把全仓库塞上下文。

### 100. 如何处理子模块？
- 要点：默认边界；显式授权。
- 30 秒：子模块是独立仓库和路径边界，默认只读或拒绝写，除非用户明确把它加入 workspace 范围。

### 101. Git diff 能作为最终正确性证据吗？
- 要点：不能；还需测试。
- 30 秒：diff 只说明改变了什么，正确性来自相关测试、静态检查和任务验收；最终回答应区分已运行与未运行。

### 102. 如何选择要运行的测试？
- 要点：受影响范围→模块→全量；预算约束。
- 30 秒：先运行失败或目标测试，再模块测试，预算允许再全量；每一步命令和结果进入审计。

### 103. 测试命令失败如何分类？
- 要点：代码失败、环境失败、超时、基础设施失败。
- 30 秒：退出码不够，要解析常见构建错误；依赖下载/daemon 不可用不能算 Agent 修复失败。

### 104. flaky test 怎么办？
- 要点：有限重跑；保留每次；标 flaky。
- 30 秒：同一未改代码有限重跑确认，不用多数投票掩盖问题；报告每次输出和分类。

### 105. TDD 在这个项目怎样应用？
- 要点：scripted model；先失败；最小实现；回归。
- 30 秒：状态机、parser、registry、store 和 eval 都先用确定性测试定义行为，再实现；外部模型测试显式开启，避免 CI 不稳定。

### 106. Mock 模型有什么局限？
- 要点：验证控制流，不验证真实分布。
- 30 秒：scripted model 能精确覆盖边界和崩溃点，但不能证明真实模型会正确选择工具，所以还需契约测试和真实 benchmark。

### 107. Provider 契约测试如何不花钱？
- 要点：录制/构造流；本地 HTTP stub。
- 30 秒：给 parser 任意切分的 SSE/NDJSON，客户端用 stub server 验证 header、状态码和断流；真实 API 只在环境变量开启时跑。

### 108. Docker 集成测试验证哪些点？
- 要点：用户、网络、资源、挂载、超时。
- 30 秒：容器内 `id` 验证非 root，网络请求应失败，检查 cgroup 限制，只能访问 workspace，并验证超时清理。

### 109. 覆盖率目标有什么意义？
- 要点：发现未测路径；不是质量本身。
- 30 秒：core 85% 行/75% 分支推动终止与错误路径测试，但不能用无断言测试刷数；安全不变量更重要。

### 110. 为什么安全测试要包含绝对路径和 `..`？
- 要点：典型绕过；跨平台组合。
- 30 秒：两者是 workspace 逃逸最常见输入，还应覆盖 symlink、UNC、混合分隔符、编码和不存在父目录。

### 111. 如何做取消？
- 要点：取消 token；HTTP/进程/虚拟线程传播；落事件。
- 30 秒：用户取消设置会话 token，停止模型 body、取消并发读、终止进程树，写 `SESSION_TERMINATED:CANCELLED` 并保留可检查状态。

### 112. 如何设计异步审批 API？
- 要点：GET pending；POST decision；幂等键；认证授权。
- 30 秒：审批资源包含版本和 call id，提交使用 compare-and-set；重复请求返回同一决定，只有授权用户可见 diff 和敏感参数。

### 113. 多用户隔离需要增加什么？
- 要点：tenant id、目录/数据库隔离、配额、密钥作用域。
- 30 秒：所有 session/event/workspace 都带 tenant，策略与费用按租户，容器使用独立挂载和凭据；当前单机 CLI 没有这些承诺。

### 114. 多 Agent 为什么首版不做？
- 要点：共享状态、协调和成本成倍复杂；先证明单 Agent。
- 30 秒：多 Agent 引入任务分解、消息一致性、并发写冲突和预算分配；单 Agent 的恢复和安全边界未稳定前不应扩大范围。

### 115. 如果以后做多 Agent，怎样避免写冲突？
- 要点：独立 worktree、所有权、合并门禁。
- 30 秒：每个 worker 用独立 worktree，只输出 commit/diff，由 coordinator 跑测试并合并；不能共享可写目录。

### 116. 为什么不默认 git push？
- 要点：外部不可逆副作用；凭据与供应链风险。
- 30 秒：本地 diff 可审查，远程 push 需要显式用户授权和更高风险策略；首版故意不暴露该工具。

### 117. 怎样把 CLI 演进成服务？
- 要点：保留 core SPI；任务队列；远程 store；异步审批。
- 30 秒：把 Picocli adapter 换 REST/queue，SQLite 换 PostgreSQL，sandbox 做 worker；AgentEngine 和 Tool/Policy 契约保持不变。

### 118. 怎样做水平扩展？
- 要点：session lease；单写者；幂等事件；共享对象存储。
- 30 秒：一个 session 同时只能有一个持租约 worker，事件 append 用期望 sequence CAS；大输出放对象存储，数据库存哈希和引用。

### 119. 生产上线前还缺什么？
- 要点：强隔离、租户、密钥、SLO、演练、真实评测。
- 30 秒：至少补 gVisor/微虚机、异步审批、租户权限、密钥服务、完整取消、灾备、OTLP、红队和多次真实 Java20；当前仓库不声称生产级。

### 120. 你从项目中最重要的思考是什么？
- 要点：Agent 质量是模型能力 × 确定性工程边界 × 证据。
- 30 秒：模型决定上限，但后端决定错误会不会变成事故、失败能否恢复、结果能否相信。我最大的收获是对不确定性做显式建模：非法参数是可修复，预算耗尽不是任务失败，未知副作用是 UNCERTAIN，环境失败不能包装成模型失败。
